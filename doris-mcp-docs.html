    1. What is a semantic model?

    A semantic model is a business description of a database table. You tell the system:

    • What the table's primary key is (entities)
    • Which fields can be used for grouping (dimensions)
    • Which fields need aggregate computation (measures)

    Once defined, users can issue natural-language-level queries ("show me monthly total order amount") and the system automatically generates the correct SQL.

    💡 In one sentence: YAML is the instruction manual, MetricFlow is the translator — it turns "monthly total order amount" into SELECT DATE_TRUNC('month', order_date), SUM(amount) FROM orders GROUP BY 1.

    2. Quick start

    Step 1: Write a YAML file

    Each YAML file describes one table. Put it under the models/ directory:

    # models/orders.yaml
---
semantic_model:
  name: orders                         # Model name
  db_table: dw.orders                    # Corresponding Doris table
  defaults:
    agg_time_dimension: order_date    # Default time dimension

  entities:
    - name: order_id                     # Primary key
      type: primary
      expr: order_id

  dimensions:
    - name: order_date                   # Time dimension
      type: time
      type_params:
        time_granularity: day
    - name: channel                      # Categorical dimension
      type: categorical

  measures:
    - name: total_amount                 # Total order amount
      agg: sum
      expr: amount
    - name: order_count                  # Number of orders
      agg: count
      expr: order_id

    Step 2: Define the time configuration

    A project.yaml is required to specify the calendar table (used for time-based metrics such as YoY and MoM):

    # models/project.yaml
---
time_config:
  calendar:
    - table: dw.dim_date
      column: date_id
      grain: day

    Step 3: Validate & commit

    1. Click 💡 Validate to check whether the model is correct
    2. Once confirmed, click Commit to make the model take effect
    3. Use list_metrics to view available metrics and query_metric to query data
    ⏱ Validation automatically checks: whether tables exist, whether column names are correct, and whether entities and dimensions are complete. If there are problems, it reports the specific error and location.

    3. Semantic model structure

    A complete semantic_model contains the following fields:

    FieldTypeRequiredDescription
    namestring✅Globally unique model name. Starts with a lowercase letter; may contain digits and underscores
    db_tablestring✅Doris physical table. Format: database.table, e.g. dw.orders
    defaultsobject✅Default configuration. Must currently include agg_time_dimension
    entitieslist✅Entity definitions for the table. Must include at least one type: primary entity
    dimensionslist✅Dimensions available for grouping and filtering
    measureslistrecommendedAggregate computation definitions. Each automatically becomes a queryable metric
    descriptionstringoptionalFree-text description of the model
    labelstringoptionalDisplay name
    primary_entitystringconditionalRequired when no type: primary entity exists
    ⚠️ Naming rules: all names (models, entities, dimensions, measures) must:
    • Start with a lowercase letter
    • Contain only lowercase letters, digits, and underscores
    • Not contain two consecutive underscores __
    • Be at least 2 characters long
    ✅ order_id, total_amount, user_count
    ❌ OrderID, order__id, a

    4. Entities — the table's "ID card"

    Entities define the uniqueness and relationships between rows. Every table must have one primary entity.

    FieldTypeRequiredDescription
    namestring✅Entity name, unique within the model
    typeenum✅Entity type (see the table below)
    exprstringrecommendedCorresponding database column. May be omitted (defaults to name); SQL expressions are also supported
    descriptionstringoptionalFree-text description
    labelstringoptionalDisplay name

    Entity types

    TypeMeaningUse case
    primaryPrimary key. Unique per row, covers all recordsThe table's ID column. Each table must have exactly one primary entity
    foreignForeign key. May have duplicates and nullsColumns referencing other tables, e.g. customer_id, product_id
    uniqueUnique key. Unique per row, may not cover all recordsUnique identifiers such as email or national ID number
    naturalNatural key. A real-world unique identifierE.g. product barcodes, employee numbers

    Example: entity definitions for an orders table

    entities:
  - name: order_id               # Primary key: unique ID of each order
    type: primary
    expr: order_id

  - name: customer               # Foreign key: references the users table
    type: foreign
    expr: user_id

  - name: order_ref              # Foreign key + SQL expression
    type: foreign
    expr: substring(trace_id FROM 1 FOR 8)
    ⚠️ Note: if the table has no type: primary entity, you can specify primary_entity: entity_name at the model's top level.

    5. Dimensions — how data is grouped

    Dimensions define how data is grouped and filtered. There are two types: time dimensions and categorical dimensions.

    FieldTypeRequiredDescription
    namestring✅Dimension name
    typeenum✅time or categorical
    type_paramsobjectrequired for timeTime granularity configuration (see below)
    exprstringrecommendedCorresponding column name or SQL expression
    is_partitionbooleanoptionalWhether this is a partition column. Defaults to false
    descriptionstringoptionalFree-text description
    labelstringoptionalDisplay name

    Time granularity (time_granularity)

    GranularityMeaningExample
    dayBy day2025-01-15
    weekBy week2025-W03
    monthBy month2025-01
    quarterBy quarter2025-Q1
    yearBy year2025
    hourBy hour2025-01-15 14:00
    minuteBy minute2025-01-15 14:30

    Example

    dimensions:
  - name: order_date               # Order date (by day)
    type: time
    type_params:
      time_granularity: day
    expr: order_date

  - name: order_month              # Order month (by month)
    type: time
    type_params:
      time_granularity: month
    expr: order_date               # Same column, different granularity

  - name: channel                   # Channel (categorical)
    type: categorical
    expr: channel

  - name: status_label             # With a SQL expression
    type: categorical
    expr: concat(status, '_', channel)

    6. Measures — aggregate computations

    Measures define aggregate operations on data columns. Each measure automatically generates a query metric of the same name.

    FieldTypeRequiredDescription
    namestring✅Measure name (also becomes the metric name)
    aggenum✅Aggregation type (see the table below)
    exprstringrecommendedColumn name or SQL expression participating in the computation
    descriptionstringoptionalMetric description
    labelstringoptionalDisplay name
    create_metricbooleanoptionalSet to false to skip metric generation. Defaults to true
    agg_time_dimensionstringoptionalOverrides the model's default time dimension

    Aggregation types at a glance

    TypeMeaningTypical usage
    sumSumTotal amount, total count
    countCountNumber of orders, number of users
    count_distinctDistinct countUnique users, active devices
    averageAverageAverage amount, average duration
    minMinimumLowest price, earliest time
    maxMaximumHighest price, latest time
    medianMedianMedian order amount
    percentilePercentileP99 latency, P95 amount (requires agg_params.percentile)
    sum_booleanBoolean sumConversion count, times a target was met

    Example

    measures:
  - name: total_amount            # Total order amount
    description: "Sum of all order amounts"
    agg: sum
    expr: amount
    label: "Total Amount"

  - name: order_count             # Number of orders
    agg: count
    expr: order_id

  - name: unique_customers        # Unique customers
    description: "Number of distinct customers who placed orders"
    agg: count_distinct
    expr: user_id

  - name: p99_amount             # P99 order amount
    agg: percentile
    expr: amount
    agg_params:
      percentile: 0.99

  - name: internal_counter       # Not exposed as a metric
    agg: sum
    expr: raw_value
    create_metric: false

    7. Full example

    Below is a complete semantic model definition for an e-commerce scenario — the orders table:

    # models/orders.yaml — orders fact table
---
semantic_model:
  name: orders
  description: "E-commerce orders fact table; each row is one order"
  db_table: dw.orders
  defaults:
    agg_time_dimension: order_date

  # ── Entities ──
  entities:
    - name: order_id
      description: "Order primary key"
      type: primary
      expr: order_id

    - name: customer
      description: "Associated user"
      type: foreign
      expr: user_id

    - name: product
      description: "Associated product"
      type: foreign
      expr: product_id

  # ── Dimensions ──
  dimensions:
    - name: order_date
      description: "Order date (by day)"
      type: time
      type_params:
        time_granularity: day
      expr: order_date

    - name: order_month
      description: "Order month"
      type: time
      type_params:
        time_granularity: month
      expr: order_date

    - name: channel
      description: "Order channel"
      type: categorical
      expr: channel

    - name: status
      description: "Order status"
      type: categorical
      expr: status

  # ── Measures ──
  measures:
    - name: total_amount
      description: "Total order amount"
      label: "Total Amount"
      agg: sum
      expr: amount

    - name: order_count
      description: "Total number of orders"
      label: "Order Count"
      agg: count
      expr: order_id

    - name: unique_customers
      description: "Distinct customers who placed orders"
      label: "Unique Customers"
      agg: count_distinct
      expr: user_id

    - name: avg_amount
      description: "Average order amount"
      label: "Avg Order Value"
      agg: average
      expr: amount

    8. Advanced metric definitions

    Besides the simple metrics auto-generated from measures, you can define advanced metrics with metric: documents. Advanced metrics combine existing measures or metrics to implement more complex computation logic. Four types are supported:

    TypeMeaningTypical scenarios
    ratioRatio metric: numerator ÷ denominatorConversion rate, profit margin, share
    derivedDerived metric: expression over existing metricsMoM growth, YoY change, weighted calculations
    cumulativeCumulative metric: accumulation over a time windowLast-7-day sales, month-to-date signups
    conversionConversion metric: conversion analysis between two eventsOrder conversion rate, signup conversion rate
    📄 File format: advanced metrics live in standalone YAML files with the top-level metric: (singular) instead of semantic_model:. One metric per file, or several separated by ---.

    8.1 Ratio metrics

    Computes the ratio of two metrics, e.g. conversion rate = orders / visits.

    # models/conversion_rate.yaml
---
metric:
  name: order_conversion_rate
  description: "Order conversion rate: orders / visits"
  type: ratio
  type_params:
    numerator: order_count       # Numerator: references an existing metric
    denominator: visit_count     # Denominator: references an existing metric

    Both numerator and denominator must be names of already-defined metrics (simple metrics or other advanced metrics).

    8.2 Derived metrics

    Computed from one or more existing metrics via an expression. Most often used for MoM and YoY comparisons.

    # models/revenue_growth.yaml — MoM growth
---
metric:
  name: revenue_growth
  description: "Revenue MoM growth rate"
  type: derived
  type_params:
    expr: (current_revenue - prev_revenue) / prev_revenue
    metrics:
      - name: total_amount         # Current-period revenue
        alias: current_revenue
      - name: total_amount         # Previous-period revenue (same metric, with offset)
        alias: prev_revenue
        offset_window: 1 month     # Shift back by one time window
    ParameterDescription
    exprComputation expression; references input metrics by their alias
    metricsList of input metrics
    nameReferenced metric name
    aliasAlias used in expr
    offset_windowTime offset, e.g. 1 month, 7 days, 1 year
    offset_to_grainGranularity to offset to, e.g. month, year

    8.3 Cumulative metrics

    Accumulates a metric over a time window, e.g. "last 7 days of sales".

    # models/weekly_sales.yaml
---
metric:
  name: weekly_sales
  description: "Sales over the last 7 days"
  type: cumulative
  type_params:
    measure:
      name: total_amount
    window: 7 days          # Time window: the past 7 days
    ParameterDescription
    measureReferenced measure name (from some semantic_model's measures)
    windowTime window format: number granularity, e.g. 28 days, 4 weeks, 3 months
    grain_to_dateOptional. Accumulate up to the given grain, e.g. month (month-to-date), year (year-to-date)

    8.4 Conversion metrics

    Measures the rate at which users convert from one event (base) to another (conversion). Commonly used to analyze user behavior funnels.

    # models/order_conversion.yaml
---
metric:
  name: visit_to_order_conversion
  description: "Conversion rate from visit to order"
  type: conversion
  type_params:
    conversion_type_params:
      base_measure:                 # Base event (visit)
        name: visit_count
      conversion_measure:          # Conversion event (order)
        name: order_count
      entity: user               # Linking entity: the dimension conversion is computed over
      calculation: conversion_rate  # Calculation method
    ParameterDescription
    base_measureMeasure name of the base event
    conversion_measureMeasure name of the conversion event
    entityLinking entity name; conversion is computed over this dimension (usually user or session)
    calculationconversion_rate or conversions (absolute conversion count)
    windowOptional. Conversion window, e.g. 7 days

    9. Common patterns

    Pattern 1: One column as dimensions of different granularities

    A single date column can define day, week, and month dimensions at the same time:

    dimensions:
  - name: order_date
    type: time
    type_params:
      time_granularity: day
    expr: order_date

  - name: order_week
    type: time
    type_params:
      time_granularity: week
    expr: order_date        # Same column!

  - name: order_month
    type: time
    type_params:
      time_granularity: month
    expr: order_date        # Same column!

    Pattern 2: Using SQL expressions

    When a column name is not intuitive enough, or a computed field is needed, use SQL expressions:

    dimensions:
  - name: user_label
    type: categorical
    expr: concat(level, '_', city)  # Concatenated field

entities:
  - name: user_short_id
    type: foreign
    expr: substring(trace_id FROM 1 FOR 8)  # Substring

measures:
  - name: net_amount
    agg: sum
    expr: coalesce(amount, 0) - coalesce(discount, 0)  # Computed field
    ✅ Supported: standard SQL functions such as substring, concat, coalesce, cast. These expressions are recognized automatically during physical validation and skip column-name checks.

    Pattern 3: Partitioned tables

    If the table has a partition column, mark it with is_partition: true:

    dimensions:
  - name: ds
    type: time
    type_params:
      time_granularity: day
    is_partition: true              # Mark as partition column
    expr: ds

    Pattern 4: Hiding internal measures

    Some measures are only meant for intermediate computation and should not be exposed to end users — set create_metric: false:

    measures:
  - name: total_amount            # ✅ Public metric
    agg: sum
    expr: amount

  - name: _raw_count              # ❌ Not exposed
    agg: count
    expr: order_id
    create_metric: false

    10. Advanced features

    10.1 Filters

    SQL filter conditions can be added to measure definitions or metric definitions. Filters are applied before aggregation.

    📍 Where filters can go:
    • The filter: field of measures — limits the data range of a single measure
    • The filter: field of a metric: — limits the data range of the whole metric
    • input_measures[].filter: on a measure — limits the measure referenced in an advanced metric
    # Example 1: measure-level filter — only sum amounts of "completed" orders
measures:
  - name: completed_amount
    description: "Sum of amounts of completed orders"
    agg: sum
    expr: amount
    filter: {{ render_dimension_template('status') }} = 'completed'

    # Example 2: metric-level filter
---
metric:
  name: premium_user_orders
  description: "Number of orders from premium users"
  type: simple
  type_params:
    measure:
      name: order_count
      filter: {{ render_dimension_template('user_level') }} = 'premium'
    ⚠️ Filter syntax:
    • Reference dimensions in YAML with {{ Dimension('qualified_name') }} or {{ render_dimension_template('dimension_name') }}
    • Reference entities with {{ Entity('entity_name') }} or {{ render_entity_template('entity_name') }}
    • Follow with a plain SQL condition, e.g. = 'value', IN ('a', 'b')
    • The where parameter of query_metric accepts raw SQL directly (e.g. "channel = 'APP'"); the compiler automatically converts it to MetricFlow template syntax

    10.2 Saved queries

    Save a common metric + grouping + filter combination as a query template that users can call directly.

    # models/weekly_report.yaml
---
saved_query:
  name: weekly_revenue_report
  description: "Weekly revenue report: total order amount and order count by channel"
  label: "Weekly Revenue Report"
  query_params:
    metrics:
      - total_amount
      - order_count
    group_by:
      - order_id__order_week      # Group by week
      - order_id__channel         # Group by channel
    order_by:
      - "-order_id__order_week"  # Week descending
    limit: 52
    FieldDescription
    metricsList of metric names to query
    group_byGrouping dimensions. Format: entity_name__dimension_name (double underscore)
    order_byOrdering; a - prefix means descending
    whereFilter conditions (same syntax as filters)
    limitMaximum rows returned
    💡 Dimension reference format: entity_name__dimension_name (double underscore). For example, order_id__order_date refers to the order_date dimension in the orders table.

    10.3 Non-additive measures & slowly changing dimensions (SCD Type II)

    Some measures cannot simply be summed (e.g. inventory levels, account balances) and need a snapshot value at a specific dimension.

    # Non-additive measure: inventory level (month-end snapshot)
measures:
  - name: monthly_inventory
    description: "Month-end inventory level"
    agg: sum
    expr: inventory_count
    non_additive_dimension:
      name: snapshot_date       # Non-additive dimension
      window_choice: max        # Take the maximum value within the time window
      window_groupings:
        - product                # Snapshot grouped by product

    SCD Type II (slowly changing dimensions): when a dimension table has an effective time range, mark the start and end dimensions:

    # Marking SCD Type II in a dimension table
dimensions:
  - name: valid_from
    description: "Effective start time"
    type: time
    type_params:
      time_granularity: day
      validity_params:
        is_start: true              # Mark as start time

  - name: valid_to
    description: "Effective end time"
    type: time
    type_params:
      time_granularity: day
      validity_params:
        is_end: true                # Mark as end time

    10.4 Null filling & time-axis alignment

    # Turn NULL into 0 (useful for count-type metrics to show 0 on days with no data)
metric:
  name: daily_orders
  type: simple
  type_params:
    measure:
      name: order_count
    fill_nulls_with: 0         # Show 0 on days with no data
    join_to_timespine: true   # Align to the time spine (fill in days with no data)
    ParameterDescription
    fill_nulls_withReplace NULL in the aggregate result with the given value (usually 0)
    join_to_timespineJoin the metric result with the time spine table so every day/month/year has a row (days without data get NULL or 0)

    10.5 Native table reference format

    Besides the db_table shorthand, MetricFlow's native node_relation format is also supported, including three-part catalog references:

    # Two-part: schema.table
node_relation:
  schema_name: dw
  alias: orders

# Three-part: catalog.schema.table
node_relation:
  database: catalog
  schema_name: dw
  alias: orders

# db_table also supports the three-part form
db_table: catalog.dw.orders

    10.6 Aggregation modes for cumulative metrics

    Cumulative metrics support three period_agg modes controlling the aggregation behavior within the time window:

    # last: take the value of the last day in the window (default behavior)
metric:
  name: end_of_week_inventory
  type: cumulative
  type_params:
    cumulative_type_params:
      measure:
        name: inventory_count
      window: 7 days
      period_agg: last       # Take the last day's value

# average: daily average within the window
      period_agg: average    # 7-day average

# first: take the value of the first day in the window
      period_agg: first      # Take the first day's value
    period_aggDescription
    lastValue of the last day in the window (default)
    averageDaily average within the window
    firstValue of the first day in the window

    10.7 Constant properties of conversion metrics

    In a conversion metric, constant_properties specifies properties that must stay the same between the two events:

    # Analyze conversion by "traffic source", requiring the source to be identical across both events
metric:
  name: visit_to_order_by_source
  type: conversion
  type_params:
    conversion_type_params:
      base_measure:
        name: visit_count
      conversion_measure:
        name: order_count
      entity: user
      constant_properties:
        - base_property: order_id__channel    # Property of the base event
          conversion_property: order_id__channel # Property of the conversion event (must match)

    10.8 Metric time granularity & offset to grain

    Metric-level time_granularity: specify the time granularity directly in a metric definition (overriding the query-time default behavior):

    metric:
  name: monthly_revenue
  type: simple
  time_granularity: month     # This metric aggregates by month by default
  type_params:
    measure:
      name: total_amount

    offset_to_grain: in derived metrics, align the offset to the given grain (instead of the default day level):

    metric:
  name: yoy_growth
  type: derived
  type_params:
    expr: (current - prev) / prev
    metrics:
      - name: total_amount
        alias: current
      - name: total_amount
        alias: prev
        offset_window: 1 year
        offset_to_grain: month    # Offset to month grain (instead of day)

    10.9 Entity roles

    The same entity (e.g. user_id) may play multiple roles in a table. In an orders table, for example, user_id is both the "buyer" and the "referrer". Distinguish them with role:

    entities:
  - name: user
    type: foreign
    expr: buyer_id
    role: buyer              # This user entity's role is "buyer"

  - name: user
    type: foreign
    expr: referrer_id
    role: referrer           # This user entity's role is "referrer"

    When role is not specified, the default role equals the entity name.

    11. Best practices

    1. One file per table. Name files table_name.yaml for a clear, maintainable structure.
      ✅ orders.yaml, users.yaml, products.yaml
    2. Define entities first, then dimensions, then measures. Entities are the skeleton of a semantic model, dimensions are its grouping ability, and measures are the query targets. Writing in this order avoids omissions.
    3. Write a description for every measure. End users see metric names and descriptions. Good descriptions let them understand a metric without reading the YAML.
    4. The same time column can define dimensions of multiple grains. For example, the order_date column can have day, week, month, quarter, and year granularities at once.
    5. Use meaningful business names for foreign key entities. The entity name customer is easier to understand than user_id — it represents the "customer" concept, not just the "user_id column".
    6. Validate first, then commit. After every YAML change, click 💡 Validate. The system verifies table existence, column-name correctness, and naming rules. Commit only after seeing a green pass.
    7. Measure names must be unique within a model. Measure names may repeat across different models, but that causes metric overriding — so keeping them globally unique is best.

    12. Common errors & troubleshooting

    Error messageCauseSolution
    Table xxx does not exist The table referenced by db_table does not exist Check the table name spelling; confirm both the database and table names are correct
    measure references missing column: dw.orders.xxx The column named in the measure does not exist in the table Check that expr matches the actual column name (mind the case)
    entity references missing column The entity's expr column does not exist Same as above; for SQL expressions (e.g. substring(...) ), confirm the function and column names are correct
    Duplicate measure 'xxx' defined in 2 models Two models define a measure with the same name Rename one of the measures to keep names globally unique
    Duplicate semantic_model name Two files use the same model name Rename one of the models
    Did not find exactly one project configuration Missing project.yaml Create a project.yaml containing time_config
    'xxx' does not match '^(?!.*__)...$' Naming violates the rules Start with a lowercase letter, remove double underscores, and use at least 2 characters
    No staging changes to validate There are no pending changes to validate Upload/modify YAML files first, then click Validate
    🔍 Quick troubleshooting steps:
    1. Confirm the table exists in Doris: DESCRIBE dw.orders
    2. Confirm column names match exactly, including case
    3. Check YAML indentation (spaces only — no tabs)
    4. Confirm all names follow the lowercase-initial rule

    13. Semantic model management in doris-mcp

    13.1 Workspaces

    A workspace is an isolated container for semantic models. Each workspace has its own:

    • Model files (YAML definitions)
    • Metric list (list_metrics only shows metrics in this workspace)
    • Query engine instance (MetricFlow compiler)
    • Doris connection pool

    Metrics in workspace A are completely invisible to workspace B. Suitable for dividing by team, project, or environment.

    📌 Naming rules: workspace names must start with a letter and may contain only letters, digits, and underscores. E.g. marketing, finance_v2.

    13.2 The three workspace states

    Call check_service_health to view the runtime status of each workspace. A workspace is always in one of these three states:

    StateIconMeaningTrigger
    healthy 🟢 Running normally. Semantic models loaded successfully; metrics are queryable. YAML files committed, bootstrap parsing succeeded, MetricFlow engine ready.
    no_models ⚪ Empty workspace. No YAML files uploaded yet. A newly created workspace, or all files have been deleted.
    not_ready 🔴 Load failed. Files exist but cannot be compiled into a semantic manifest. YAML syntax errors, missing tables, missing project.yaml, MetricFlow validation failures, etc. Check the validate error message. 
      ┌──────────────┐   upload YAML    ┌──────────────┐   commit OK       ┌──────────────┐
  │  no_models   │ ──────────────→ │  not_ready   │ ───────────────→ │   healthy    │
  │  (empty)     │                 │  (needs fix) │                  │  (running)   │
  └──────────────┘                 └──────────────┘                  └──────────────┘
                                         ↑                                  │
                                         │       upload broken YAML         │
                                         └──────────────────────────────────┘
    📊 Version tracking: after every reload the system records the version number, metric count, and whether loading succeeded. Use the metric_count returned by check_service_health to confirm the number of currently loaded metrics.

    13.3 Active Store and Staging Store

    Each workspace has two storage layers inside:

    LayerTable namePurpose
    Active Store
    (live)    		active_store_{workspace}Committed and loaded models. The query engine uses this version. Files are read-only.
    Staging Store
    (pending)    		staging_store_{workspace}Pending changes uploaded or edited by users. Supports add/edit/delete. After passing validation, they are committed into Active.
       Staging Store               Active Store
  ┌─────────────┐   commit    ┌─────────────┐
  │ edit / add  │ ─────────→ │  query use  │
  │ validate ✓  │            │  read-only  │
  │ discard  ✗  │            │             │
  └─────────────┘            └─────────────┘
       ↑                          ↑
   user edits               used by the query engine

    13.4 Update flow

    Semantic model updates follow the edit → validate → commit → auto reload flow:

    StepActionDescription
    1Upload/edit YAMLFiles enter the Staging Store (running queries are not affected)
    2💡 ValidateMandatory! The system automatically checks: table existence, column-name correctness, YAML syntax, MetricFlow semantic rules, naming rules, cross-model duplicate names
    3🚀 CommitStaging → Active. The system automatically triggers an engine reload (no manual restart needed)
    4⟳ Auto reloadA background thread parses the new models, compiles the JSON manifest, and updates the function routing. Usually completes in 2-5 seconds
    ⚠️ Validate before commit: a Staging set that has not been validated is rejected by Commit with "Staging must be validated before commit".

    1.3 Available tools at a glance (10 tools)

    🟢 Startup & health check (call these first when starting a conversation)

    ToolParametersPurpose
    get_query_guide — Mandatory first call. Returns the full workflow guide: when to use the semantic layer vs raw SQL, tool call order, and query syntax. Without this tool the agent wastes time.
    check_service_health detail (optional) Returns Doris connectivity + the state of each workspace (healthy / no_models / not_ready) and metric counts. Call it at the start of every conversation.

    📊 Semantic queries (preferred; correct SQL generated automatically)

    ToolParametersPurpose
    list_metrics workspace (required), page_size, page_token Lists all available metrics (name + description). The agent matches metrics against user intent.
    list_dimensions_for_metric workspace (required), metric_name (required) Returns the metric's available group_by dimensions (name + type + description). Ensures group_by does not fail.
    query_metric workspace (required), metrics (required), group_by, where, order_by, limit, having, database, max_rows Core query tool. Compiles + executes semantic queries. Use it for anything involving counts/sums/ratios/rankings/trends. Supports HAVING to filter aggregated results. database specifies the target database; max_rows hard-caps returned rows (0 = default 10000).
    reload_semantic_layer workspace (required) Manually triggers a semantic layer reload. Call it after an admin edits and commits YAML models if immediate effect is needed; otherwise auto-polling runs every 60s.

    🔍 Low-level metadata & raw SQL (use only in these two scenarios)

    ⚠️ The two raw SQL scenarios:

    • Scenario A — semantic layer unavailable: check_service_health shows no workspace in healthy state (all no_models / not_ready). All queries must then go through list_databases → list_tables → describe_table → execute_query.
    • Scenario B — no matching metric: the semantic layer is healthy, but no metric in list_metrics matches the user's intent. Fall back to the raw SQL path in this case as well.
    ToolParametersPurpose
    list_databases page_size, page_token Lists all databases. Useful during exploration, but it cannot replace list_metrics.
    list_tables database (required), like, page_size, page_token Lists table names in a database. Returns names only, no column info. Use describe_table for columns.
    describe_table database (required), table (required), detail_level Shows the physical table structure (column names, types). detail_level: names/summary/full.
    execute_query sql (required), database, max_rows Raw SQL fallback. Read-only only (SELECT/SHOW/DESCRIBE/EXPLAIN). If the semantic layer has a matching metric, prefer query_metric.

    1.4 Recommended agent workflow

    🔁 Standard flow for every conversation:

    1. get_query_guide() — get the full guide (the agent learns which tool to use when)
    2. check_service_health() — confirm Doris connectivity and view available workspaces
    3. Routing decision:
      • "how many", "calculate", "trend", "ratio" questions → use the semantic layer, steps 4-5-6
      • "show table structure", "which databases" questions → use the metadata tools
      • Semantic layer unavailable (no workspace healthy) → skip 4-6, go straight to 7
    4. list_metrics(workspace) — list metrics and match the user's intent
    5. list_dimensions_for_metric(workspace, metric_name) — get the available dimensions
    6. query_metric(workspace, metrics, group_by, ...) — execute the query
    7. Fallback: if step 4 finds no matching metric, use list_databases → list_tables → describe_table → execute_query for the raw SQL path

    🚫 Hard rules:

    • Semantic layer healthy + matching metric exists → never bypass query_metric and write SQL with execute_query.
    • Semantic layer healthy + no matching metric → first tell the user "the semantic layer does not cover this query", then use execute_query, and include a warning in the result.

    5. FAQ

    Q: Cannot connect, getting 401

    Check the token format: username:password (separated by an English colon).

    Q: Semantic query fails with "workspace not found"

    Confirm the workspace name is correct; the default "example" works. Log into the WebUI to see available workspaces.

    Q: Can I execute write operations?

    No. execute_query only allows read-only SQL (SELECT / SHOW / DESCRIBE / EXPLAIN).

    Q: Queries are slow?

    With large data volumes, have the AI add LIMIT or narrow the time range.

    Q: Which metrics can the semantic layer use?

    Check quickly with the CLI:

    doris-mcp-client tool call list_metrics --json '{"workspace":"example"}'
doris-mcp-client tool call check_service_health
